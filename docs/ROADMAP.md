# 里程碑

目标：达到 Minecraft Java Edition **Release 1.0.0**（2011-11-18）特性面的 80%+，实际按 90+ 规划。
评分细则见 [RUBRIC.md](RUBRIC.md)。

排序原则：**最不确定的技术风险最早退休**。三个真未知是 (a) 零依赖工具链、(b) worker + 流式加载的帧预算、
(c) 客户端/服务端边界重构 —— M0 干掉 (a)，M3 在还没有内容拖慢之前干掉 (b)，M2 先在同线程里引入
`ServerCore` + `Transport`，于是 M5 的 worker 拆分是搬一个已经长成边界形状的代码库，而不是重写 4 万行。

## M0 完成记录（2026-08-29）

**交付**
- 零依赖工具链：`tools/dev-server.mjs` 用 Node 内置 `module.stripTypeScriptTypes` 现场剥离类型直接喂浏览器；
  剥离保留空白，行列号与源码逐字符对齐，因此不需要 sourcemap，DevTools 栈直指 `.ts` 原位
- 供应工具：esbuild 0.25.12（`tools/bin/esbuild.exe`）、TypeScript 5.9.3、@types/node 22.20.1，
  全部由本机既有安装复制而来，**零下载**
- CI 门禁 `tools/ci.mjs`：tsc → lint-erasable → lint-layers → lint-size → node:test → smoke
- 无头验证：`tools/cdp.mjs` 用 Node 24 内置 WebSocket 直接驱动 CDP，**不需要 Puppeteer**
- `src/core/rng/java-random.ts`：位级复刻 `java.util.Random`
- `src/core/math/`：vec3 / mat4，全部 `(out,...)->out` 零分配形式
- `src/core/noise/perlin.ts`：Perlin + 倍频 + 脊状，置换表由 JavaRandom 洗牌
- `src/core/constants.ts`：MC 1.0 数值真相来源
- 客户端第一帧：原生 WebGL2 + **12 字节顶点格式** + **TEXTURE_2D_ARRAY** + 程序化贴图 + 自由飞行相机
- `window.__mc` 测试钩子 + 截图哈希回归

**验收证据**
- `node tools/ci.mjs` 6 步全绿
- JavaRandom：与 BigInt 参考实现交叉验证 10 项全过，且命中两个独立的 JDK 已知输出锚点
  （`new Random(0).nextInt() = -1155484576`、`new Random(42).nextInt() = -1170105035`）
- lint 实测能拦：`enum`、跨层 import、缺 `.ts` 后缀、DOM 全局泄漏、渲染层读挂钟、裸模块说明符，
  且报出精确行号
- 无头 Chrome 真 GPU（ANGLE D3D11）渲染 968 面 / 1 次 draw call / fps 180
- 截图哈希跨有头与无头环境完全一致（`overview = 4e9f9d7c`）；故意改坏黄金值会以退出码 1 拦下
- 截图：`tests/out/{overview,closeup,topdown}.png`

**过程中修掉的真问题**
1. `mat4.fromCamera` 右向量符号写反 —— 正交性检查发现不了（翻转不破坏正交性），
   靠与 `lookAt` 的交叉验证抓到
2. Chrome 后台标签页 rAF 完全不派发、`setTimeout` 也被节流到 1 Hz，
   自动化会挂死 → 改用 worker 心跳驱动后台帧
3. `setCanvasSize(640,360)` 被 `resizeToDisplay` 按 dpr=1.5 改成 960×540，
   破坏跨机器可比 → 加尺寸锁
4. CDP 在页面导航中求值报 "Cannot find default execution context" —— 竞态，
   改为先开空白页建会话再导航并等 load，另加有限重试
5. smoke 存的 PNG 原是整个视口（含 HUD 与黑边），与被哈希的 canvas 内容对不上 →
   改成直接存 `__mc.screenshot()` 的结果

**已知遗留**
- Chrome 走的是 Intel 集显而非 RTX 5060。M3 做性能验收时要确认这一点是否影响结论
- `simple-mesher.ts` 是 M0 的临时实现：无 AO、无贪心合并、不跨区块。M1 已替换

## M1 完成记录（2026-08-29）

**交付**
- `core/world/chunk.ts` —— `Chunk` / `ChunkSection`，扁平 `Uint16Array`（id 12bit | meta 4bit），
  YZX 下标，增量维护 heightmap，空气段不分配
- `core/world/block-view.ts` —— `BlockView` / `MutableBlockView` / `ChunkStore`，
  让一份碰撞、一份射线、一份光照同时服务客户端镜像与服务端世界
- `core/block/` —— `BlockDef` + 13 个行为钩子契约 + 基础类型
- `core/registry/` —— 注册表 + **冻结时烘焙的扁平属性表**（热路径只读 typed array）
- `core/net/codec.ts` —— ByteWriter / ByteReader，帧长度用 u32
- `core/world/chunk-codec.ts` —— 调色板 + 位打包的区块序列化，以及 18³ padded 邻域抽取
- `core/math/aabb.ts`、`core/math/frustum.ts`（Gribb-Hartmann 平面提取）
- `content/blocks.ts` —— 46 种方块，**沿用 MC 1.0 的真实 id**
- `client/mesh/mesher.ts` —— 完整网格化：18³ padded 邻域、3 采样 AO、平滑光照、
  四边形翻转消对角线接缝、三渲染层分离
- `client/render/` —— 贴图配方（51 张原创像素画）、图集与面层号烘焙、
  `ChunkRenderer`（每层一个 VAO、视锥剔除、半透明按距离排序）

**验收证据**
- 15 个 mesher 测试 + 14 个 chunk 测试全过；`node tools/ci.mjs` 6 步全绿
- **UV 有逐角断言**（前作的致命 UV bug 正是因为没有这个才带到线上）
- 编解码往返对随机内容逐格比对，覆盖 4bit / 8bit / 无调色板三条分支
- heightmap 的增量维护与全量重算逐格一致（放置与破坏两个阶段分别验证）
- 无头渲染 25 区块 / 70 段 / 32714 面 / 89 draw call / fps 180
- 4 个视角的截图黄金哈希：`tests/screenshots/hashes.json`

**过程中修掉的真问题**
1. `crossPlant` 的默认参数让 TS 把 tint 推成字面量 `0`，传 `TintKind.GRASS` 就报错 —— 显式标注
2. **草方块整块被染绿**，包括侧面本该是泥土的部分。tint 原本是方块级的，
   改成**按面掩码**（`tintFaces`）—— 顶点格式里 tint 本来就是逐顶点的
3. **alpha 渗色**：`noiseFill` 给透明像素写 `rgb(0,0,0)`，`generateMipmap` 把黑色平均进
   相邻不透明像素，树叶出现黑斑。改为透明像素也填基色，并加通用的 `bleedEdges()` 后处理
4. **小屋盖在树上**：`surfaceY` 返回的是最高非空气方块，遇到树就返回树叶高度。
   不透明木板压住下方树叶，天光归零，画面上是一大片黑斑 —— 一开始极易误判成
   mipmap 或 cutout 的渲染 bug。靠**扫描实际光照数据**（61 个天光为 0 的树叶，
   坐标正是小屋位置）才定位到，修完从 61 降到 0

> 第 3、4 条都表现为"树叶发黑"，但成因完全不同，一个在贴图生成、一个在世界内容。
> 教训与 docs/RULES.md 第 14 条一致：不要凭现象猜，去读实际数据。

## M2 完成记录（2026-08-29）

**交付**
- `core/net/` —— 声明式包 schema（一次定义派生编解码与类型）、21 个数据包、
  Transport 抽象（Loopback / MessagePort）、带批量与 u32 分帧的 PacketChannel
- `content/biomes.ts` —— 14 个 1.0 群系，含地形参数、地表方块、染色、装饰密度
- `server/world/gen/` —— 完整生成流水线：
  - `biome-source` 群系选择 + **5×5 邻域加权的高度过渡**（避免群系边界的刀切感）
  - `terrain-gen` **3D 密度场**（粗网格 + 三线性插值 + 逐列细节噪声）
  - `caves` 真正的 perlin worm（方向被噪声持续扰动）+ 峡谷
  - `ores` MC 的椭球矿脉算法，严格按 1.0 的 Y 带表
  - `surface` 逐格暴露判定的地表处理、基岩、结冰
  - `decorator` 橡树/云杉/花草，跨区块两阶段生成
- `server/world/sky-light.ts` —— 垂直柱 + 水平 BFS 泛洪
- `server/` —— `ServerCore`（**不含 Worker/DOM 依赖**）、`ServerWorld`、`ServerPlayer`
  （订阅差集推送、按距离排序、节流）
- `client/world/client-world.ts` —— 客户端镜像与子区块级脏标记
- 客户端改为**完全通过协议**接收世界

**验收证据**
- 11 个世界生成测试：同种子逐格一致、生成顺序无关、悬垂存在、洞穴连通、
  矿物 Y 带精确、群系多样、跨区块装饰
- 13 个 ServerCore 测试：含**长跑 20000 tick**（时间回绕正确、区块不泄漏）
- 14 个协议测试：全包随机往返、100 KB 大包不串流
- `ci.mjs` 6 步全绿；smoke **连跑 5 次全部通过**
- 群系分布实测：海洋 23.8%、平原 20.2%、森林 15.8%、山地 10%、蘑菇岛 0.1%
- 世界生成性能：22 ms/区块（从最初 48 ms 优化而来）

**过程中修掉的真问题**
1. **噪声阈值全部错位**。倍频 Perlin 归一化后 σ≈0.18、p95≈0.28，而群系阈值是按
   "值域 [-1,1] 均匀分布"写的 —— `hill > 0.42` 之类几乎永不成立，山地/沙漠/雪原
   整类凭空消失。加 `stretched2` 把分布拉开后阈值才有意义。
2. **地形退化成高度图**。`FREQ_Y=0.0115` 时垂直噪声在 4-8 格内只变化 0.043，
   而 `FALLOFF=0.72` 需要 4.3，差两个数量级，一处悬垂都产生不了。
3. **粗网格插值造成规则梯田**。加逐列细节噪声打破（每区块仅 256 次噪声调用）。
4. **光照全量重算卡死浏览器**。RD=6 时每 tick 要扫 370 万格，实测 45 秒无响应。
   改为只处理脏区块。
5. **区块推送顺序影响光照**。A 推送后邻居 B 才加载，B 的泛洪改了 A 的光照但
   A 的快照早已发走 —— 世界画面取决于区块到达先后。改为推送前先生成 3×3 邻域。
6. **半透明绘制顺序不确定**。距离相同的段按 Map 插入顺序绘制，而那取决于网格化
   完成的先后。会导致水面闪烁。排序加 sectionKey 次级键。
7. **邻域生成的区块永不卸载**。它们从未被"订阅"，订阅差集清不掉，服务端无限堆积。
   加按玩家视野的保留集扫描。
8. **出生点可能在树里**。findSpawn 用的是装饰前的地形阶段。握手时按完整世界再校正。

**关于截图回归的确定性**

M2 花了相当篇幅让 smoke 变得可复现，因为它是后续所有里程碑的验收基础。
关键是三件事：
- `waitForIdle` **主动 pump 模拟**而不是等真实时间（服务端 tick 原本由帧率驱动，
  "跑到第几 tick"取决于机器快慢）
- 空闲判据必须同时包含客户端网格化队列**和服务端待推送队列**
- 测试模式关闭热重载（意外 reload 会清空 `__mc` 与世界状态）

定位过程中写了 `tools/probe-determinism.mjs`：它对世界数据做指纹，
用来区分"世界数据不确定"还是"渲染不确定"。三次跑世界指纹完全一致，
才把范围缩到渲染层，进而找到半透明排序的问题。

**已知遗留**
- 服务端与客户端同线程，世界生成阻塞渲染（M5 解决）
- 网格化在主线程（M3 解决）
- 水/雪/方块光/光照变暗传播的临时状态见 docs/DEVIATIONS.md

## M3 完成记录（2026-08-29）

**范围调整**：原计划把服务端 worker 化放在 M5，但 M3 的性能验收（fps≥55）直接依赖它 ——
实测服务端在主线程时，玩家一移动帧率就从 60 掉到 19。既然瓶颈明确，就在 M3 一并做了。
M5 相应改为"SAB 时钟与 worker 边界加固"。

**交付**
- `client/mesh/mesh-worker-pool.ts` + `entry/mesh-worker.ts` —— 网格化 worker 池。
  worker **完全无状态**：只在启动时收一份只读方块表，每个任务自带 18³ 邻域快照。
  输入缓冲随结果一起还回来进空闲池，稳态分配趋近 0。
- `entry/server-worker.ts` —— 服务端 Worker 宿主，带漂移自校正的 tick 循环。
  ServerCore 本身一行没动，只是换了个 Transport —— 这正是当初抽象传输的目的。
- `S_ServerStats` 包 —— 服务端搬进 Worker 后主线程读不到它的内部状态，
  自动化与 F3 面板都需要这个。
- 每 tick 的**区块生成配额**：按区块数而非耗时计，以保住确定性。

**性能验收（RD 8，飞行 300 格，1500 帧采样）**

| 指标 | 标准 | 实测 |
|---|---|---|
| fps 中位 | ≥55 | **59.4** |
| fps p10 | — | 54.8 |
| fps 最低 | — | 40.6 |
| 堆漂移 | <20 MB | **3 MB** |
| drawCalls 峰值 | <1200 | **382** |
| 待网格 / 在飞 / 待推 | 归零 | 全为 0 |
| 服务端稳态 tick | — | 0.3 ms |
| 错误 | 0 | 0 |

无头环境的 fps 从 9 提升到 **180**（服务端不再阻塞主线程）。

**世界生成性能：48 ms → 11.6 ms（4.1 倍）**

优化是靠**分段计时**找出来的，不是猜的：

| 阶段 | 优化前占比 | 做了什么 |
|---|---|---|
| 洞穴 | 66% | 方向噪声 3 倍频降到 2 倍频；峡谷加水平预剔除；整条隧道的粗包围盒剔除 |
| 矿脉 | 22% | 保持不变（Y 带必须忠实 1.0） |
| 地形 | 7% | 群系网格批量预算（625 次 biomeAt → 81 次） |
| 群系/地表 | 5% | — |

洞穴降倍频后一度让洞穴总量掉到阈值以下（113 格 vs 150）——
因为倍频越少标准差越大，扰动过强导致隧道更快钻出 y 范围而终止。
改成 y 边界**反弹**而非终止后恢复。

**过程中修掉的真问题**
1. **`recountBytes` 是 O(n)**，每次 upload 都遍历全部 section 累加字节数。
   900 段 × 每帧 12 次 upload = 每帧三万次迭代。这就是 1% 帧掉到 6 fps 的元凶，
   改成增量维护后**最低 fps 从 6.0 提升到 40.6**。
2. **光照 BFS 种子过多**。垂直柱之后把每个有光的格子都入队，一个区块三万多个，
   十几个区块几十万个，光是出队检查邻居就把服务端拖到 1 TPS。
   改为只有"某个水平邻居的地表比自己高"的格子才入队 —— 开阔地带的格子四周
   本来就都是满值，往外传播不改变任何东西。
3. **`waitForIdle` 会在世界还没开始加载时误判安定**。服务端在 Worker 里启动要时间，
   那之前三项统计全是 0 且不变，于是拿到一个空场景（实测 quads=0）。加 chunks>0 下限。
4. **`press` 按帧数计时不合理**。"按住 1 秒"实际等的是 60 帧，真实帧率低于 60 时
   就超时报错，而那本是正常的性能表现。改按墙钟计。
5. **`setInterval` 采样在后台标签页失真**。71 秒只采到 6 个点。改用帧回调采样。

**已知遗留**
- **首次加载慢**：RD 8 约 25 秒。配额只决定工作量怎么摊，不改变总量；
  真正的解法是把区块生成也拆进独立的 gen worker（原计划 M3 的一部分，
  实测服务端 worker 化后已能满足帧率目标，故推迟）。→ M5
- fps p10 为 54.8，略低于 55 的线。中位与平均都达标，尖峰来自跨区块边界时的批量网格化。


## M4 完成记录（2026-08-29）

**做完的事**：双通道光照引擎（天光 + 方块光）、增量更新、昼夜循环、MC 光照贴图模型。

### 一个概念性错误，以及它花掉的时间

天光最初被我写成"垂直向下穿过透明方块不衰减"。这个规则**是错的**，而且错得很隐蔽：

- 它不符合 MC。MC 里天光没有任何垂直特例，靠的是 heightmap ——
  `y >= 该列最高挡光方块 + 1` 的格子直接给满值（`canBlockSeeTheSky`），
  其余一律按 `max(1, 遮光度)` 六向衰减。十格深的竖井底部之所以还是 15，
  是因为那些格子**本来就见天**，不是因为光垂直传下去没衰减。
  反过来，大树冠下面在 MC 里确实随深度变暗 —— 所以树底下会刷怪。
- 它还破坏了增量更新的**算法前提**。increase/decrease 双队列的正确性依赖
  "光沿传播方向严格递减"；一整列 15 彼此相等时，移除时"更暗的邻居才是下游"
  这个判据就失效了。

症状极难定位：随机操作跑到第 37 次才出现 47 处偏差，且只在特定地形下显形。
我先后试过特判、按列重算、以变更点为中心的局部全量重算（半径 17），
都只是把偏差推得更远一点，直到回去核对 MC 的真实模型才找到根因。

**教训写在这里**：当一个增量算法怎么修都差一点点时，先去核对**规则本身**，
而不是继续修算法。

### 交付

- `core/light/light-engine.ts` —— 两条通道共用一套 BFS 与双队列移除。
  天光的垂直部分完全由 heightmap 决定，BFS 内部因此严格单调，双队列才成立。
- `core/world/day-night.ts` —— 昼夜，全部复刻 MC 原式：
  `celestialAngle` / `skyLightSubtracted` / `sunBrightness` / `lightBrightness`。
- 着色器改用 MC 的光照贴图模型：两条通道各自过非线性亮度曲线后**相加**再夹到 1。
  天光红绿再乘 `(sun*0.65+0.35)` 而蓝不乘 —— 太阳一落山天光自动偏蓝；
  方块光先放大 1.5 倍再按 0.6/0.4 曲线压绿压蓝 —— 火把偏暖。
  这个色差就是"洞口冷、火把边暖"的来源。
- 客户端镜像跑**同一份** core 算法做增量更新。服务端不为一次方块变更下发光照数据。
- `__mc` 新增指令通道：`command` / `setTime` / `setBlock` / `checkLight` / `remeshCount`。

| 项 | 标准 | 实测 |
|---|---|---|
| 增量 vs 全量逐格一致 | 相等 | 3 个种子 × 300 次随机操作，**逐格全等** |
| 黄金光照场景 | 4 个 | 10 个（见天/屋檐渗透/玻璃树叶/火把/移除/跨区块/双光源…） |
| 昼夜截图 | tick 0/6000/13000/18000 | 4 张哈希互不相同且稳定 |
| 地下改一格的重网格化 | ≤4 段 | **2 段** |
| 空中改一格（整列阴影） | — | 5 段 |
| 光照开销 | ≤5 ms/tick | **2.96 ms/tick**（0.49 ms/区块 × 配额 6） |
| 增量更新 | — | 0.057 ms/次 → 20 次/tick 只要 1.1 ms |

光照播种从最初的 4.92 ms/区块降到 0.49 ms（**10 倍**），分四步：
只给"邻居地表更高"的格子入队（4.4×）、跳过最高已分配子区块之上的写入、
缓存列高、以及**一个 tick 内的新区块统一播完再扩散一次**（2.1×，
逐块扩散时相邻新区块会一轮轮互相灌光）。

### 顺带修掉的三个真问题

1. **空气段的天光在两端读出来不一样**。地表以上的空气段不会被分配，
   服务端写 15 时会把它分配出来，而这些段不进区块包，客户端解出来是 0。
   同一格服务端读 15、客户端读 0。改成**隐含值**：未分配的段按
   `y >= heightmap ? 15 : 0` 读，两端一致，还省掉了每列三四个段的分配。
2. **斜角邻居到达后不会触发重网格化**。mesher 拿的是 18³ 邻域，四个斜角也在里面，
   但 `onChunkData` 只标记了上下左右。斜角后到的段会永远保留"斜角还不存在"时
   算出的网格 —— 同一个种子跑两遍，收敛后的画面能差几千个面。
   这是截图哈希偶发不匹配的**真正**元凶。
3. **`waitForIdle` 信的是过期数据**。它读的 `S_ServerStats` 每隔若干 tick 才发一次，
   相机刚移动完时手里还是移动**之前**那份，于是读到"没有待推送区块"就返回，
   然后在截图中途才把新区块补上。改成同步的 `settled` 指令往返 ——
   指令走包队列，服务端处理它时必定已处理完之前的移动包。

另外 `screenshotHash` 现在要求**连续两帧哈希相同**才采信，
把"偶尔有个网格结果姗姗来迟"从碰运气变成显式等待。

### 试过但回退的

给服务端加了 `pause` 指令想在截图期间冻住世界。实测**更不稳定**：
连跑 7 次，ground/skyline 每次都给出不同的哈希 —— 暂停会把世界钉在
"某个区块刚到货、还没网格化"的瞬间。已回退。真正的解法是上面的第 2、3 条。

### 心跳线程

后台标签页会把 worker 里的 `setTimeout` **彻底掐死**。实测前台 20.0 TPS，
切到后台后 30 秒内一个 tick 都没跑（指令往返 8 秒超时，连一次 flush 都没做到）。
对内置服务端来说，这意味着切出去泡杯茶回来，作物没长、熔炉没烧、怪没动。

`Atomics.wait` 不是定时器，是让线程睡在 futex 上，不受节流影响。但它**阻塞整条线程**，
所以不能放进服务端 worker —— 那样 MessagePort 的消息永远等不到事件循环。
于是拆成两条线程：`clock-worker` 只负责睡觉和敲鼓，服务端 worker 保持事件驱动。
跨线程 postMessage 不是定时器，同样不受节流。

顺带加了 `core/shared-stats.ts`：一小块 SAB，各线程往自己的槽里写计数。
读它是一条内存指令，不需要对方的事件循环转起来 —— 这在诊断"后台是不是停摆"时
是决定性的，因为节流会同时掐死问和答，用消息去问只能得到一个超时。

### 生成 worker

生成一个区块 9.6 ms，一个 tick 只有 50 ms。留在服务端线程里，加载期间
79 个 tick 有 62 个超预算，服务端等于在以 10 TPS 跑。

搬进 `gen-worker` 之后 tick 立刻降到 p50 2.19 ms，但**总时长反而从 8 秒涨到 16.5 秒** ——
因为 `ensureChunk` 不再当场返回区块而是下个单，于是"发不出去就停下"把流水线
卡成了串行：下单 → 等一个 tick → 收货 → 发一个 → 再下单。
加上**预取**（每 tick 沿待办队列往前 24 个，先把邻域都下单）之后降到 4.0 秒。

`ServerWorld` 通过 `ChunkProvider` 接口拿区块，自己不认识 Worker ——
`node --test` 里仍然是同线程生成，ServerCore 及其以下不含任何 Worker 依赖。

### 这一轮挖出来的三个真 bug

都是"不报错、不掉帧，只是画面不对"的那一类，靠一条新断言逼出来的：
**强制整场重做网格后，画面必须一模一样**。

1. **区块到达时不重做斜角邻居**。mesher 拿的是 18³ 邻域，四个斜角也在里面，
   而 `onChunkData` 只标记了上下左右。斜角后到的段会永远保留"斜角还不存在"时
   算出的网格。
2. **区块卸载时完全不重做邻居**。邻居当初把朝向本区块的面剔掉了，本区块一走
   那些面就该重新出现 —— 否则**视距边缘会看穿世界**。这个的排查过程很绕：
   强制重做后画面变了、多出上万个面，而世界数据逐格相同、mesher 顶点字节
   1007 段全等、绘制顺序也有确定的次级键。最后才想明白是相机移动导致
   订阅集合平移，边上的区块被卸载了。
3. **截图用例没钉死时间**。天色与光照取决于"截图那一刻世界跑到了第几 tick"，
   而那取决于加载花了多久。M5 把加载从 8 秒缩到 4 秒，于是**一整批哈希集体变化**，
   看上去像渲染坏了。现在每个用例都强制 `setTime`。

第 3 条尤其值得记：一个"回归测试"如果依赖挂钟，它迟早会把一次**性能改进**
报告成一次**渲染回退**。

### 五个 MC 原值逐个吻合

| 项 | MC 1.0 | 本项目 |
|---|---|---|
| 终端速度 | 78.4 格/秒 | **78.40** |
| 跳跃高度 | 1.2522 格 | **1.2522** |
| 行走 | 4.317 格/秒 | **4.3172** |

一开始三个速度**同时**高出 2.05%（4.405 / 5.727 / 1.322）。三个数被同一个
系数拉偏，是"漏了一处公共乘数"的指纹 —— 找到是 `EntityLivingBase.onLivingUpdate`
里的 `moveStrafing *= 0.98F; moveForward *= 0.98F`。补上之后三个数分别落位。

它还解释了一个副作用：**斜着走恰好快 1/0.98 = 2.04%**。直走时输入长度 0.98 < 1，
`moveFlying` 的 `if (len < 1) len = 1` 不把它放大回去；斜走两轴各 0.98、
长度 1.386 > 1，归一化后拿到满额加速度。不是老式 FPS 那种快 41% 的斜跳，
但也不是严格相等。

### 挖掘时间

| | MC 1.0 | 本项目 |
|---|---|---|
| 徒手挖石头 | 7.5 秒 | 7.5 |
| 木镐挖石头 | 1.15 秒 | 1.15 |
| 钻石镐挖石头 | 0.25 秒 | 0.25 |

用的是 MC 的原式（`速度 / 硬度 / 30`，不能收获时除 100），不是"硬度 × 1.5"
那种简化式 —— 简化式在"能收获但工具不对口"（拿铲子挖石头）这类上会算错。

途中发现 `ToolTier.WOOD = 0`，于是**没有办法表达"徒手就能收获"**：
`minTier` 默认 0 会被当成"需要木级工具"，一开局连泥土都挖不到。
补了一个 `requiresTool`，默认按"是否用镐"推导（正好覆盖 1.0 的全部方块）。

### 服务端权威

挖掘的**破坏时刻由服务端自己算**，客户端发的 `FINISH_DIG` 只当作"松手"。
信客户端的话，改一行前端就能瞬间挖穿基岩。有一条专门的测试锁这个：
只发 FINISH_DIG 不该破坏任何东西。

客户端本地也算一份进度，**纯粹为了画裂纹**。两边跑同一份
`core/block/breaking.ts`，所以裂纹涨满的那一刻和服务端判定破坏的那一刻重合。

### 顺带修掉的

- **物理没有 tick 间插值**。物理固定 20 Hz、画面 180 fps，直接把身体位置
  喂给相机的话每 9 帧才动一次 —— 是"20 fps 的卡顿"。按 partialTick 插值后正常。
  这个是被验收脚本逼出来的：逐帧采样时发现只有 1/9 的帧有位移。
- **上台阶会失速**。原来无条件在碰撞轴上清零速度，于是每上一级半砖都顿一下，
  走楼梯一路一顿。改成只清"抬高之后仍然被挡住"的轴。
- **碎屑是白的**。草和树叶的贴图是灰度的，颜色靠群系染色乘上去 ——
  粒子着色器没乘，挖草掉白渣。玩家不会意识到自己在读这个信息，但缺了就是不对。
- **client-main 顶到 600 行硬上限**，被 lint 拦下。把交互层拆成
  `client/player/interaction.ts`。这正是那条规则的用处：它逼着人把长出来的
  东西搬走，而不是继续糊。

### 验收脚本本身的一段弯路

"按住 W 一秒走多远"这条断言改了四版才稳定：

1. 一秒总位移 —— 出生点旁边有树，走 2.2 格就撞上了
2. 100ms 窗口取中位数 —— 采样点不对齐帧，一帧的位移被劈给两个窗口
3. 0.4 秒滑窗取最大 —— 物理是 20 Hz 离散跳，窗口里落 8 步还是 9 步取决于对齐，
   取最大必然偏高（实测 4.61）
4. **按物理 tick 度量，取每 tick 位移的中位数** —— 稳定在 0.2101 格/tick，
   四次跑分毫不差

教训和 M5 的"截图没钉死时间"是同一个：**验收脚本自己也会带偏差**，
而它带的偏差看起来永远像是被测代码的问题。


## M7 完成记录（2026-08-29）

**做完的事**：数据驱动的方块模型系统，一次加进 14 种非立方体方块。

### 模型是数据，不是分支

模型 = 一组带贴图与剔除信息的盒子（`core/block/block-model.ts`），
坐标单位 1/16 格，和 MC 的 JSON 模型一致。加一种新形状 =
写一个返回 `BlockModel` 的函数，**mesher 一行分支都不用加**。

没有这一层的话，每种非立方体方块都要在 mesher 里加个 if，到第五种时
mesher 就没法读了 —— 前作正是这么烂掉的。

模型按**状态**（id × 16 + meta）索引：楼梯朝向、栅栏连接、门开合都在元数据里。
冻结时把 16 个元数据各烘一份并结构化去重，几十种方块最后只有 60 个模型。

### 新增的 14 种方块

半砖、双层半砖、木楼梯、石楼梯、栅栏、火把、梯子、玻璃板、雪层、蛋糕、
木门、活板门、床、铁轨。

### cullface 是这套东西里最容易写错的一处

一个面只有**正好贴着格子边界**时才允许被邻居剔除。半砖的顶面在 y=8，
不贴边界，所以上面压一块石头也必须照画 —— 标成可剔除的话，
半砖上放东西会看穿，而这在静止截图里几乎发现不了。

所以 cullface 由 `autoCullface` 从坐标推导，不让内容作者手写，
并且有一条专门的 mesher 测试盯着它。

### 碰撞盒由模型推导，不另存一份

改了模型忘了改碰撞的后果是玩家卡在看不见的东西上，而且极难复现
（得从特定角度走特定路线）。现在两者是同一份数据的两种读法。

顺带把 M6 留下的 `collisionHeight` 删掉了 —— 那本来就是模型系统的占位。
M6 里"半砖上台阶"那条测试当时只能用一张改过高度的合成表，
现在换成了**真正的半砖**。

### 验收

### 窗口是物品栏的视图，不是它的副本

搬运会在切换的瞬间产生"东西还没到位"的窗口期，而那正是多人环境下

取走产物时按"每个非空格各扣一个"而不是"按配方图样扣" ——
这是唯一和平移/镜像匹配自洽的做法：配方可能是镜像匹配上的，
按图样去扣会扣错格子。

### 界面

这类 UI 最经典的 bug（看着点在格子上，实际点中旁边那格）。

122 个物品图标全部程序化生成，按原型分类（锭 / 宝石 / 粉末 / 工具 / 剑 /
盔甲 / 食物 / 容器）。同一类物品共用同一个形状、只换配色 —— 这是 MC 自己的做法，

### 一个查了很久的空白界面

而 NaN 顶点同样既不报错也不画）。

### 存档为什么是同步的

`ServerCore.tick()` 全程同步，是"`node --test` 直接手动 tick 两万次"这条
验证路径的地基。所以整条存档路径刻意保持同步：NBT 不 gzip（改用 RLE）、
区块编解码是纯函数、region 常驻内存。**只有最后"字节 → 磁盘"那一步是异步的**，
而它跑在两次 tick 之间，JS 单线程保证了中间没人能改世界。

代价是压缩率不如 gzip；收益是"世界 → 字节"这一段可以在测试里逐字节比对，
"同一个世界存两次字节必须相同"就是一条普通断言。

### 一个会永久丢数据的顺序问题

第一版读档测试挂在"柱子第 0 格没还原"。查下去发现：玩家登录时会
`forceChunk` 强制生成出生区块，而那一刻存档的 region 还在异步读盘的路上。
于是出生区块被**新生成的地形覆盖**，等 region 到货时那里已经有一个区块了，
`installFromSave` 再也走不到。

这类丢失没有任何直接症状 —— 玩家只会发现"重进游戏房子没了"。所以修法是两条：
1. `SaveController.loadLevel()` 预载出生点与玩家所在处的 region，宿主
   **必须先开存档再放客户端进来**；
2. `ServerWorld.forcedOverPendingSave` 计数器把违反这条不变式的情况记下来，
   持久化测试断言它是 0 —— 把静默的数据丢失变成一条会失败的断言。

### 两条"测试自己错了"

- 熔炉进度对不上，差**正好 40**，而 40 正是我在读档后跑的 tick 数 ——
  熔炉装回来之后接着烧了，那是对的行为。改成"在它刚回到世界、还没被 tick 过
  的那一刻取值"。
- 掉落物读档后数不到，因为它落到玩家头上被捡走了。改成先直接
  `forceChunk` 取回区块验存档，再跑 40 tick 验"读档→下落→拾取"整条链路。

两次都是验收脚本自带的偏差，而它们看上去都像被测代码的 bug —— 与 M4、M8
同一类教训。

### 一条写死了测试名的开关

和存档毫无关系。实际原因是 `index.html` 的热重载开关判的是
`test=smoke` 这个**字面量**，而新脚本用的是 `test=persist` ——

### 流体的四步与那个 −1.1 式的教训重演

算法照抄 MC 的 `BlockFlowing.updateTick`：按邻居定级 → 无限水源 → 先向下 →
再按"哪个方向最快找到洞"向旁边。第四步是"水会拐弯找洞"的全部来源，
也是这套模拟里唯一贵的部分（每个方向一次深度 4 的搜索）。

踩到的坑和 M10 的骷髅瞄准同一类：我把"落下来的水"当成**不给邻居供水**，
而 MC 是把它当**满格**（`if (i1 >= 8) i1 = 0`）。后果是瀑布底下的水算出
"我没有邻居"就把自己删了，下一刻又被灌满 —— 一个永不收敛的来回，
表现是计划刻队列永远清不空、水面一直在闪。测试②在修之前跑满 600 刻不收敛，
修完 70 刻就稳。

### 爆炸的两个数据错误

一发 TNT 在实心石头里炸出 **137** 格，是 MC 的两倍多。两个原因：

1. 石头的爆炸抗性走了 `hardness × 5` 的通用启发式得到 7.5，
   而 MC 给整个石头族显式写的是 `setResistance(10)`
2. 每步的强度衰减我写成 `STEP × 0.225`，MC 是**固定** `0.225`，与步长无关。
   乘上步长后每步只扣 0.0675，射线能跑三倍远

两处都改对之后是 76 格，正是 MC 的量级。这一条又一次说明：能照抄的常数
就照抄，自己估的每一个数都是一处将来要查的 bug。

  站得太远、右键**根本没到达服务端**。把玩家挪近之后才真正测到

### 红石为什么不照抄递归顺序

MC 的递归邻居通知产生了 BUD、准连接这些位置相关的行为 —— 玩家会利用，
但它们也公认是 bug。复刻它要逐行照抄 Java 的调用栈。

这里改成**连通分量整体重算**：找出相连的全部线 → 取相邻电源的直接功率 →
从高到低传播。用"按功率分桶"代替优先队列，因为功率只有 0..15 十六档，
从高往低扫一遍就能保证每格拿到最大值。

### 三个"接线接漏了"

- **75 与 94 从来没注册过**。MC 用两个 id 表示同一个元件的开与关
  （火把 75/76、中继器 93/94），而 M7 只注册了一半。红石逻辑一切换状态
  就写进一个没有定义的 id：方块存进去了，但没有模型、没有贴图、查表全是

- **线网重算走 setBlockQuiet，所以线变亮不会自己往外扩散**。一条十五格长的
  线，尽头那个火把永远收不到消息 —— 拉杆一拉线全亮了，火把纹丝不动，

### 自动改代码的那次翻车

拆完发现 69 个 import 因为代码搬走而变成死的，于是写了个脚本按
`tsc --noUnusedLocals` 的报错自动删。脚本删完自己跑了一遍 tsc，报告"干净"。

实际上它把 `server-core.ts` 里五个**多行** const 的声明行删掉了，留下孤儿函数体：

```
/** 少数几个"掉的不是自己"的方块 */      ← 注释还在
  1: 4,    // 石头 -> 圆石              ← 声明行没了
  2: 3,    // 草方块 -> 泥土
};
```

文件根本编译不过。脚本没发现，是因为它的"干净"判定只 grep 了
`TS6133 | TS6192` 这两个码 —— 它自己制造的 `TS1005` 语法错误全被过滤掉了。

**教训：自动改代码的循环，终止条件必须是"编译器完全没话说"，不是
"我关心的那类报错没有了"。** 一个只看得见自己预期错误的修复器，
制造的新问题正好落在它的盲区里。

修完之后把 `noUnusedLocals` 写进了 `tsconfig.json` 常开。死 import 不只是噪音：
它让"这个模块依赖谁"的答案是错的，分层 lint 会跟着一起误判。

### 顺手修的行尾

仓库长到这里已经是混的：106 个文件 LF、41 个 CRLF —— 因为写文件有两条路径
（Write 工具在 Windows 上写 CRLF，脚本和 heredoc 写 LF），谁最后动过决定了行尾。
后果不是不好看：一次脚本化批量改动会把几十个文件整体重写，真改动淹在几千行
行尾 diff 里，review 直接失效。加了 `.gitattributes` 钉死 `eol=lf`。

> 本次提交因此包含一次全仓行尾归一。想看真正的改动：
> `git diff --ignore-cr-at-eol <M12 hash> HEAD`

### waitForIdle 从"等多久"改成"还在不在动"

拆分收尾时 CI 里两个闸门同时红了，报的都是 `waitForIdle 超时 (30000ms)`。
单独重跑却过了 —— 是**假失败**。

原来的判据是一个 30 秒死线。RD 8 冷启动要经两个 gen worker 流式生成约 270 个
区块，机器一忙就压线，于是同一份代码在 CI 里时而绿时而红。更糟的是它红的时候
什么线索都不给：只说"超时了"，不说卡在哪、还在不在动。

改成看**进展**：形状（服务端待推 / 已订阅 / 已加载 / 客户端区块 / 待网格化）
一变就重新给足 8 秒，一直不变才判卡死。两头都变好了 ——

| | 旧（死线 30s） | 新（停滞 8s） |
|---|---|---|
| 慢机器上正常流式加载 | 压线，随机红 | 只要还在动就等，绿 |
| 真卡死 | 30 秒后报"超时" | 8 秒后报**卡住前后的两个形状** |

兜底上限取 45 秒，压在 `tools/cdp.mjs` 那个 60 秒的 `Runtime.evaluate` 之下：
兜底必须先触发，否则上层看到的是一句没有信息量的 CDP 超时，
而不是带着形状的报错。

这条和 M12 记的那条是同一件事的两面 ——
**验收脚本自带偏见，而那个偏见看起来永远像是被测代码的 bug。**
这次的偏见是"世界应该在 30 秒内加载完"，它把"机器忙"误判成了"代码坏"。

### 十六、音频收尾（提交 `cde3dc9`）

音效原来是靠 WebAudio 的节点图**当场合成**的：node 里跑不起来，
于是只能断言参数表（"石头的截止是 800"），断不了真正发出来的声音。
参数对而合成错（包络反了、噪声段没接上、归一化除零）照样是一片静音，
而那种退化没有任何测试拦得住。

把波形做成纯函数（`core/audio/sound-render.ts`）之后：
node 里能逐字节哈希；引擎改成"预渲染成 AudioBuffer 再播"，
于是**只有一份实现**（两份迟早会分叉，而分叉出来的症状是
"测试全绿但听着不对"）；顺带更省 —— 每次播放不再现搭一张节点图。

环境音与背景音乐的调度（`core/audio/ambience.ts`）同样在 core：
"什么时候该响"能逐刻断言。时间挂在**服务端刻**上而不是帧或挂钟上，
与"渲染代码禁止读挂钟"是同一条纪律的另一面。

顺带修掉两处工具问题：行走速度验收在慢机器上必然失败
（`clock.dt` 有 0.1 秒上限截断，3.8fps 的容器里模拟时间只有真实时间的
六成，一个完全正确的实现按墙钟量也只有 2.86 格/秒）—— 改成问客户端
跑过多少步物理，按每 tick 位移算；以及菜单截图金值还没录、
日志却写"ok"。

### 一、天空（提交 `313bd9c`）

穹顶 + 日月 + 1500 颗星 + 云层。数学放 core（`core/world/sky.ts`）而不是
client/render，为的是能在 node 里断言 —— 月相尤其：8 张各画各的，
肉眼看每一张都"像个月亮"，但连起来会在某一天跳形状。所以测的是
**8 张之间的关系**（单调、亏盈镜像、跨天步长与相邻步长同量级）。

四个渲染 bug，都是先量再改：

| 现象 | 真因 |
|---|---|
| 云全部消失 | 距离在顶点着色器算好当 varying 传，而平面四角到相机**等距**，插值出来是常数，淡出系数全平面为 0 |
| 正午天上挂着月亮 | 天体四边形写成 `-distance`，而 `celestialAngle` 正午为 0 即"不旋转"—— 未旋转时的位置就该是正午太阳的位置 |
| 云是一片噪点 | `CLOUD_SCALE` 当成了"整张图多少格"，于是一个云格只有 0.75 格宽 |
| 夜里云是灰白亮斑 | 自己凑的亮度公式午夜给 0.69。改用 MC 现成的 `sunBrightness` |

最后一条又一次印证了那条规约：**MC 有的常数就照抄，自己估的数都是将来的 bug**。

### 二、天气

状态机（`core/world/weather.ts`，纯的）+ 世界后果（`server/world/weather-tick.ts`）。
时长常数全部照抄 1.0：

| 当前 | 下一段（刻） | 折合 |
|---|---|---|
| 正在下雨 | nextInt(12000) + 12000 | 10–20 分钟 |
| 没下雨 | nextInt(168000) + 12000 | 10–150 分钟 |
| 正在打雷 | nextInt(12000) + **3600** | 3–13 分钟 |
| 没打雷 | nextInt(168000) + 12000 | 10–150 分钟 |

强度每刻 ±0.01 地爬，即 100 刻（5 秒）淡入淡出。天不会一瞬间黑下来 ——
这 5 秒是整个系统里唯一让人觉得"天变了"而不是"画面切了"的东西。

**天气不只是画面**：`isDaytime` 多了 rain/thunder 两个参数，于是雷暴天的
白天天光扣减越过 3，怪会刷、僵尸不烧。这不是给天气加的特判，是天光曲线
自然给出的结果 —— 但也正因为它是"自然给出的"，一旦哪天有人忘了传参，
天气就会悄悄退化成纯滤镜而不报任何错。所以那条单独有一个测试盯着。

### 三、`BIOMES[id]` 是错的

`precipitationOf` 一开始写的是 `BIOMES[biomeId]`。**群系 id 不连续** ——
8 和 9 留给下界与末地 —— 所以从下标 8 起数组下标就和 id 对不上了：
`BIOMES[12]` 是蘑菇岛，而不是 id 为 12 的冰原。

于是雪原下雨、蘑菇岛下雪。不报任何错，要盯着一片特定地形看很久才看得出来。
`content/biomes.ts` 里本来就有处理稀疏 id 的 `getBiome`，我没用它。
补了一个不抛异常的 `findBiome`，并在注释里把这个坑写死。

### 四、雨画了四版

| 版本 | 问题 |
|---|---|
| 1 | 距离传成 varying（同天空那个 bug），雨带整片消失 |
| 2 | 贴图是 11 列**从头到尾**的实线 —— 渲染出来是一幅静止的半透明帘子。一块处处相同的东西往下滚是看不出在动的，雨的下落感全部来自**间隙** |
| 3 | 改成短丝之后又太浓：视野里叠着上百条雨带，每条都画清楚，叠出来是一堵白墙 |
| 4 | 单条压到 alpha 55–110，且近处（<1.2 格）额外淡出 —— 相机就站在中心那一列里，那条几乎与视线共面，一条能糊住半个屏幕 |

另外 `textureLod(..., 0.0)` 强制最高级 mip：雨丝在贴图里只有一两像素宽，
而雨带是斜看的窄条，GPU 会选到很高的 mip，那一级上雨丝早被平均成一片糊。

### 五、又两个"测试自己错了"

- **`client.last('S_BlockUpdate')` 取最后一条**。随机刻每刻都在改别处的方块，
  最后一条多半不是自己挖的那格。这个坑 M13 踩过一次、只修了放置那一处，
  同一个文件里另一处一模一样的写法留到了现在 —— 靠"恰好没被撞上"活着。
  天气状态机每刻从共享随机源取数，把 RNG 流挪了两格，它就露出来了
- **雨的贴图测试用 alpha > 128 数像素**。而雨是**故意画得很淡**的，
  且雨丝头尾还要再淡一档（那是速度感的来源）。阈值 40 正好把两头切掉，
  量出来的平均段长比雪还短 —— 看着像"雨不是竖的"，而那纯粹是尺子的问题

第二条还顺带改了度量方式：从"最长连续段"改成"**平均**连续段长"。
最长段分不出"一条雨丝"和"三片雪花恰好叠在一起"，而后者是随机撒点
必然发生的巧合，画面上完全看不出异样。

### 六、粒子

`content/particles.ts` 是一张数据表（重力、阻尼、初速、尺寸、寿命、染色、
淡出），十种粒子之间的差别几乎全是**数值**而不是行为 —— 写成十个类的话，
每个类里有意义的代码只有一行构造函数。

`gravity` 取负数就是会上升的粒子。烟、火焰、气泡和碎屑的全部区别就在这个
符号上，不需要为"往上飘的粒子"单开一套代码。

**环境粒子照抄 MC 的 randomDisplayTick**：每刻在相机周围的 32³ 盒子里随机挑
420 格，挑中什么就冒什么。直觉做法是遍历附近所有方块给每个火把发一粒烟 ——
那是三万格的扫描、每刻一次。随机采样把它压到几百次，代价是单根火把的冒烟
节奏不均匀，而那恰恰更像真的。

### 七、"它让画面永远不静止"—— 第三次遇到同一件事

环境粒子上线后，两项**早于它**的检查开始失败：网格收敛与萤石夜景。

原因和 randomTicks、和野生生物是同一个：粒子每刻都在动，而截图是按帧拍的，
拍到第几帧取决于机器多快。地下十几格外的一洼岩浆就足以让每一帧都不同。

所以加了 `?particles=0`，和 `persist=0 / mobs=0 / randomTicks=0` 并列。
**验证这个判断的方式是让哈希回到原值**：关掉之后 night-glowstone 回到了
`5fcbd144` —— 一字不差是它加粒子之前的黄金值。那是证据，不是推断。

粒子本身照样被验证：`__mc.stepParticles(n)` 把随机源复位再跑固定刻数，
走的是**和正常路径同一份**发射器与物理。

### 八、两个"画得太讲究"

- **烟画成了齿轮**。第一版是一个主圆 + 四个偏移的小团 + 五个抠掉的小孔，
  想让每粒烟形状各异。但烟在屏幕上只有几十像素，那些凸起和孔洞成了
  **主要**特征。改成单纯一团三次方衰减的柔边圆云 —— 形状的变化交给
  尺寸与寿命的随机，在同一张贴图上照样成立
- **截图里一粒烟都看不见**。环境采样是稀疏的（一根火把十几刻才轮到一次），
  20 根火把跑 150 刻也只有 9 粒，散在整片平台上。数值上验得了，
  图上什么也没有 —— 那样的"证据"等于没有。加了一次爆炸（事件那条路，
  一次三十几粒挤在一起）才让图有东西可看。
  顺带发现爆炸粒子只活二十来刻：先发爆炸再跑 150 刻的话它们早没了，
  表现是"加了爆炸粒子数一点没变"

### 九、又两次拆分

`client-main.ts` 第四、第五次顶到 600 行。两次都找到了闭包足迹小的块：

- `entry/client-session.ts` —— 起服务端、发指令、持有服务端权威的世界状态
  （时间、天气、统计）。只要 URL 参数和两个日志回调
- `entry/client-meshing.ts` —— 网格化的派发端。rev 校验与在飞上限这两条
  纪律只在调度这一层成立，正好和算法（跑在 worker 里）分开

没有拆包处理与测试钩子那两块：它们各自闭包着二三十个局部变量，
硬拆出去换来的是一个没有类型的 deps 大袋子，那比长文件更糟。

`tools/smoke-checks.mjs` 拆出 `smoke-visual-checks.mjs`，分界线是
**断言的是什么**：前者断言数值与状态，后者断言的就是那张图。
分开的实际好处是纪律 —— 后一类每项都会往世界里加东西，而它们必须还原回去。

### 十、F3 与点阵字模

要画 F3 就得先能画字，而在此之前 UiRenderer 只有一个 3×5 的**纯数字**字模。
于是补了 `client/ui/font.ts`：5×7 手工点阵，95 个可打印 ASCII，
一行一个字符、7 段用 `/` 隔开，源码里能直接看出字形。

这条验收永远是绿的，因为它比对的画面里压根没有 F3。

`debug-overlay.ts` 负责**把数摆在屏幕上**。混在一起的话，想调一下版式

### 十一、这一轮挖出的五个坑

前四个都是**早就存在、只是没人碰到**的：

1. **`UiRenderer.flush()` 从不清空这一批**。同一帧里第二次 flush 会把
   第一批连同第二批一起再画一遍。F3 是第一个需要分两批画的东西，
   这个 bug 也就是那时才露头。"flush 之后这一批就没了"是批处理器
   该有的语义
2. **超过 1024 个矩形就悄悄丢弃**。F3 一屏要两千八百多个，
   于是右下角那几行直接没了，而且不报任何错。上限提到 4096，
   并且记下丢弃数 —— 悄悄少画一块是最难查的那种 bug
3. **萤石夜景、方块陈列阵、形状近景、粒子四项都拿"当前相机"当位置基准**，
   而它们跑在一长串检查之后，相机停在哪完全取决于上一项干了什么。
   黄金值实际上绑死在检查的**顺序**上 —— 往中间插一项新检查（F3 就是），
   后面每一张图都会无端变掉，报出来却是"萤石夜景变了"。
   全部改成以 SPAWN 为基准。这个文件开头本来就写着这条纪律
4. **方块陈列阵一直是在暴雨里拍的**。天气是全局状态，而
   `smoke.mjs` 那批黄金截图的最后一张正是 thunder。雨恰好糊住了
   陈列阵要验的东西。现在每一项都像 setTime 一样显式设 `weather clear`
5. **裂纹检查的采样频率由网络延迟决定**。它在同一个循环里既采样进度
   又用 `command('getblock')` 问服务端挖穿了没有 —— 而后者是一次往返、
   好几帧。快的时候记到 10 级，慢的时候只记到 3 级，同一份代码时绿时红。
   报出来是"10 级叠加没生效"，听起来像裂纹功能坏了。
   改成每帧采样、每 10 帧才问一次服务端，跑三遍是 10 / 10 / 8

### 十二、F3 的黄金图钉住了遥测

F3 上有帧率、堆内存、服务端刻数 —— 这几个数**天生每次都不同**，
黄金图永远对不上，而那不是 bug。

所以 `setDebugOverlay(on, pinned)` 的 pinned 模式把它们换成固定值。
这么做不算作弊，因为分工是清楚的：

| | 验什么 |
|---|---|
| 截图哈希 | 它画进 canvas 了、位置对、字认得出 |
| `debug-overlay.test.ts` | 每一行的**内容与格式**，用假的 UiRenderer 逐条断言 |

后者顺带抓到两个真问题：小写 `p` 比 `e`/`a` 高一行（"Heap" 读成 "HeaP"），
以及负坐标的区块内相对坐标要落在 0..15（`-18 % 16` 在 JS 里是 `-2`）。

### 十三、贴图与 GUI 重做

起因是第一次系统地看整批截图：几何、光照、昼夜、天气都到位了，
短板集中在**贴图质感**和**界面立体感**。完整计划与取舍见
[ART-PLAN.md](ART-PLAN.md)，这里只记结论与踩到的坑。

#### 白噪声不是像素画

原来所有贴图都走 `noiseFill` —— 逐像素独立的白噪声。16×16 上它的观感
是电视雪花点：单像素在变，但相邻像素毫无相关性，退开一步被眼睛平均成
一片糊。换成可平铺的格点噪声（`valueNoise`）之后明暗才成团。

`speckles` 还有个更实的毛病：它从随机点画 `size×size`，而 `set()` 越界
**直接丢弃** —— 靠右靠下的斑点被切掉一半、靠左靠上永远没有半个，
于是同一张贴图铺成墙时接缝处一侧密一侧疏。改用环绕写入（`setWrapped`）。

两个原语最后都从 `texgen.ts` **删掉**了。留着下一个人会顺手再用一次。

#### 真正的分水岭是**调色板量化**

成团只解决了一半。量化前实测每张贴图有 **27–59 种**不同颜色（256 像素），
而手绘像素画通常只有 **4–10 种**。颜色一多，相邻像素之间就是连续渐变，
观感是"喷枪扫过"；颜色一少，每块色都有清楚的边界，才是"一格一格点的"。

`quantize(k)` 用**确定性** k-means（质心初值取亮度分位点，不是随机撒点 ——
贴图必须逐字节可复现）。在 `buildAtlas` 里对所有贴图统一施加，默认 6 色，
渐变类（日月、火）与多色相类（书架、南瓜脸）另给。全图集 265 张，
一次性开销 36 ms。

**这一步之后有个连带规矩**：量化是最后一道，配方里任何"很淡的东西"
都会被并进底色。砂岩的层理就是这么没的 —— 线画了，量化完一条不剩。
现在层理与底色的差是按"要能活过量化"设的。

#### 噪声给不了的东西：手绘结构

MC 的圆石是**六到八块能一个个数出来**的石头，中间夹深色缝。
随机撒团做不到这个：位置不受约束，团与团大量重叠，铺出来只是
"一片有明暗的灰"。改用抖动网格（`stoneCluster`）—— 把 16×16 切成
cells×cells，每格放一块石子，中心在格内抖 ±25%，于是天然留缝
又不排得像瓷砖。圆石 3×3、沙砾 4×4。

原木侧面同理：连续的竖条纹读起来像布，树皮要的是**几道明确的深沟 +
沟旁的亮棱**（`barkRidges`）。

#### GUI

面板与槽位原来是两层纯色矩形，配色是拍脑袋的 0.78 / 0.86。
换成 MC 的实际调色板（`#C6C6C6` / `#8B8B8B` / `#555555` / `#373737`）
加 Windows-95 式斜面：外凸面板左上白右下深灰，内凹槽位反过来。
槽位尺寸正好等于步进 18，相邻槽位严丝合缝拼起来 —— MC 那种连成一片的
格子网就是这么来的。

物品图标另外统一加了轮廓与体积感（`outline` / `formShade`），
放在 `buildAtlas` 里而不是每个配方里：122 件物品是按原型派生的，
写进原型会漏掉手写特例，写进配方要改一百多处。

前五个都不是这轮改坏的，是被改动照出来的：

这是黄金截图这套办法的固有盲区，加多少张图都补不上，只能靠肉眼看。

### 十四、资源包覆盖层

起因是"想要原版材质"这个需求。**把 Mojang 的 png 提交进仓库不行** ——
那是再分发，公开仓库会被 DMCA。所以把它翻译成一个功能：
`client/render/resource-pack.ts` 在启动时按名字覆盖程序化图集，
素材由使用者自己指定、留在自己盘上，一个字节都不进 git。

```bash
node tools/dev-server.mjs --pack "<解开的资源包目录>"
# 浏览器开 http://127.0.0.1:8080/?pack=/pack/
```

逐张覆盖，包里没有的退回程序化生成 —— 只解出十几张也能用。
名字映射（`pack-names.ts`）要同时试 1.13 前后两套命名：MC 那次"扁平化"
把 `log_oak` 改成了 `oak_log`、目录从 `blocks/` 改成 `block/`。

`--pack` 挂在**同源**的 `/pack/` 下，不是另起一个静态服务器 ——
本服务器给所有响应打了 `COEP: require-corp`（SAB 时钟需要），
跨域资源会被直接拦掉。

#### 一个错得很隐蔽的优化

候选路径是 6 个目录 × 若干候选名。要是对每张贴图都把 6 个目录全试一遍，
255 张就是上千次注定 404 的请求。第一版想省这个开销，做法是
"命中过的目录记下来优先试，没命中过的只在探索预算内试"。

**那是错的**：预算被**未命中**消耗，于是只要前十来张贴图恰好都不在包里，
预算就在第一次命中之前烧光了，之后再也不去看那个目录。
表现是"覆盖 0 张"，而包明明是好的 —— 直接拿 4 个名字调加载器 4 张全中，
走真实启动路径 255 个名字却 0 张。

改成显式的**探测阶段**：拿几个任何资源包都该有的文件名（`stone`、`dirt`、
`oak_planks`……）去试每个目录，试出哪些目录是活的，之后只在活目录里找。
与"要找哪些贴图"完全解耦，不会再被未命中带偏。

#### 渲染层禁止读挂钟

加载器本来用 `Date.now()` 做超时预算，被 `lint-layers` 拦了 ——
`client/render/` 下禁止读挂钟（动画相位必须来自 `clock.renderTick`，
否则 `freeze()` 停不住、截图回归失效）。

改成**请求数**预算 + 每请求 `AbortSignal.timeout`。这比原来更好：
次数是确定的，同一个包跑两次发一样多的请求，行为可复现。
"被 lint 逼出更好的设计"这事在这个项目里已经不是第一次了。

### 十五、水、岩浆、火的贴图动画

在此之前**所有贴图都是静态的**，而 MC 1.0 的水、岩浆、火都是逐帧动画的 ——
一片死水是画面上最不像原版的一处。

#### 做法：图集多帧层 + 顶点着色器换帧

动画帧作为额外的图集层排在静态层**之后**，每 16 层一组。
顶点着色器里一行：

```glsl
if (layer >= uAnimStart) layer = layer - ((layer - uAnimStart) % uAnimFrames) + uAnimFrame;
```

排在后面而不是原地展开，是为了让静态贴图的层号仍等于它在 names 里的下标 ——
mesher 烘的 faceLayer 表、UI 取图标、粒子取层号全都直接用 `index.get()`。
而动画贴图的 `index` 则**改指向动画区的第 0 帧**，否则着色器只凭层号
认不出"这一面要换帧"。

帧本身是把第 0 帧整体**滚动**出来的，不是逐帧手画：这几张贴图本来就无缝平铺，
平移一像素仍然无缝，滚满一圈正好回到起点，所以循环天然闭合。
流动的水/岩浆向下滚，火向上滚正好读作火苗上窜。速度差靠**每帧滚多远**表达，
不靠帧数 —— 所有动画同帧数，着色器里一个 `uAnimFrame` 就够。

#### 这次没有第五次踩"画面永远不静止"

前四次（存档、野怪、随机刻、环境粒子）都是加完才发现截图回归开始飘。
这次没有，而且**不是因为小心**，是因为 `capture.ts` 的 `pinFrame()`
早就把这条路堵死了：它在每次截图前把 `renderTick` **归零**。
那份注释里甚至已经把"水与岩浆的贴图帧"列为动画相位之一 ——
写它的时候这个功能还不存在。

代价是**验证方式得换**：`screenshotHash` 永远渲染在第 0 帧，动画对它不可见。
第一版拿它验，三次拿到同一个哈希，看上去像"动画没接上"，
其实是量错了东西。冒烟里那项最后走的是 CDP 原始截屏（不经过 pinFrame），
全程冻结、只用 `step()` 推 renderTick，于是画面里唯一会变的就是动画帧。

#### 顺带修掉一个一直在偶发失败的检查

加动画的过程中"生物"那项开始报"画面 12 帧内始终没稳定下来"。
查下来与动画无关：`screenshotHash` 每次重试之间会 `pumpWorld()` 推进世界，
而刚刷出来的九只生物正在各自寻路，于是每一帧都不一样，**永远稳不下来**。
它以前能过纯粹是"恰好赶上生物都站住了"。

而那张图的哈希**根本不参与比对**（golden 里没有 `mobs` 这一项）。
为一个没人比对的哈希要求画面静止，付出的是一个会偶发失败的测试 ——
规约明写着"一个 flaky 的测试比没有测试更糟"。改成直接出图，
真正要断言的"生物被提交给 GL 了"由 `mobVerts` 保证。

## M15 下界 + 要塞 + 附魔 + 酿造（2026-08-31）

提交 `56dda54`（维度 + 下界 + 传送门）、`c89f099`（附魔 + 酿造 + 恶魂）、

### 维度架构

加维度这件事在 `ServerWorld` 里是**零改动** —— 它对生成器的全部要求
只有 `generate(cx,cz)` 与 `findSpawn()` 两条。M2 把这个接缝留出来的时候
还没有第二个维度，到这里才兑现。

改动尽量收在接缝上：`core.world` 仍然是主世界（一百多处引用里绝大多数
—— 红石、流体、熔炉、合成 —— 在任何维度逻辑都一样），真正要区分的地方
走 `core.worldOf(player.dimension)`。下界与末地**按需懒创建**：
不然四百个单元测试每个都要白搭两个世界。

每刻的世界级步骤改成遍历已加载的世界。区块卸载的保留集**按维度分开**
—— 合成一个的话，去过一次下界就再也卸不掉那边的区块了。

### 下界

3D 密度场 + 上下基岩夹层，中间是连通的洞穴系统。岩浆海面 31（1.0 的数）。
实测 35% 空气 / 49% 地狱岩 / 6.5% 岩浆。

第一版把"两头夹"的偏置写反了（离边界越远越实心），结果整个维度只有
9.7% 空气 —— 一块走不进去的实心砖。测试里留了这条下限。

### 传送门

几何是纯的（`core/world/portal.ts`），能在 node 里用一张手写的假地图逐格断言。
1.0 的门固定 2×3，角可以缺。**造门与认门共用一套校验** —— 两份实现漂移的话，
玩家每回来一次就会多造一座门，几次之后目标点周围会长出一片黑曜石林。

站满 4 秒才传送（不然在自家门口会被反复吸进吸出）、传送后 5 秒冷却
（不然在两个维度之间无限弹跳）。这两个数不是节流，是**可逆性**：
门是个 2×3 的洞，走路时很容易蹭到边。

客户端收到 `S_ChangeDimension` 要**先清空整份世界镜像**再落点。
不清的话新维度的区块会一块一块盖在旧的上面，没盖到的地方还留着上一个
维度的地形 —— 症状是"下界里有一片草地"，看起来像生成器疯了。

### 附魔

21 种附魔的完整表，id 沿用 MC 的 0-6 / 16-21 / 32-35 / 48-51 ——
那些断开的号段不是随意的，**高 4 位就是装备种类**。

一处与 MC 对不上的实现被测试逼了出来：附魔力的材质加成写成了
`nextInt(j/4)`，MC 是 `nextInt(j/2)`。差这一半的后果很具体 ——
钻石装 30 级最高只到 40 附魔力，而锋利 V 要 45，于是
"三十级附魔永远出不了锋利 V"。这类问题只有**统计断言**看得出来：
单跑一次什么都证明不了。

报价在放上装备的那一刻**锁住**：不锁的话玩家可以反复拿起放下刷报价，
而"要不要花这 30 级"这个决策就消失了。

### 酿造

药水用 damage 位域编码（低 4 位效果、高位增强/延长/投掷），照抄 MC ——
于是一瓶药水还是一个 `{id, damage}`，不必往物品栏塞 NBT，
而物品栏的序列化已经在网络协议里定死了。

一份材料同时酿三瓶：这是酿造唯一的效率来源，也是"先囤三个水瓶
再开酿"这个习惯的由来。做成一瓶一份的话整套酿造会慢三倍。

### 恶魂与可击回的火球

**火球做成"生物"而不是"子弹"**：玩家要能看见它、瞄准它、打到它，
而生物那条链路（出生/移动/销毁 + `C_AttackEntity`）恰好就是这一整套。
箭走的是另一条路，服务端算完就完，客户端根本看不见。

击回按玩家的**视线方向**重设速度，不是原路返回 —— 原路返回的话
侧身一挥就能把火球送向谁也没瞄的方向，看起来像随机。

直击伤害 6 点，与爆炸分开算。这是测试逼出来的：爆炸半径只有 2 格，
而恶魂 4 格宽，火球碰到外壳时爆心离中心已经 2.6 格，正好在伤害范围外
—— 只靠爆炸的话"把火球打回去"在数值上完全没有效果，
而画面上却是结结实实炸在脸上。

### 要塞

三座，均匀分布在 640..1152 的圆环上（1.0 的数，它决定了"找要塞要走多远"
的量级）。位置**只依赖种子**：末影之眼、生成器、激活判定三处都要问这个
问题，各算一遍必然漂移，而漂移的表现是"眼睛指向的地方什么都没有"。

激活判定**从要塞的定义位置反推那十二格该在哪**，不数附近有几块带眼的
框架 —— 数数会被玩家自己摆的框架骗到。

一处如实记录的简化：MC 的要塞是几十种部件递归拼接出的迷宫，这里是
一条主走廊串起若干房间、尽头是传送门房间。见 DEVIATIONS。

## M16 末地 + 末影龙（2026-08-31）

提交 `1f7fd73`。

主岛的距离衰减用**平方**而不是线性：线性会得到一个规整的圆锥，
而 MC 的末地是中间厚、边缘很快变薄然后断成崖。岛是一块**板**，
不是填到底的世界 —— 悬浮感全在这里。

龙战写成一台**状态机**而不是一个 Goal：龙的行为取决于还剩几个水晶、
血量到了哪一档，塞进 GoalSelector 会让"按优先级抢通道"那套机制
去表达阶段，两边都变难懂。

水晶每 10 刻回 1 血。200 血 + 10 个水晶 = 玩家每秒要打出 20 点才追得平，
而钻石剑一下才 7 —— **"必须先拆水晶"这条规则的全部来源就是这个数**。
一刻只回一次、不叠加：叠加的话血条纹丝不动，玩家完全读不出发生了什么。

### 换维度暴露出来的四个真问题（都不是末地独有的）

1. **龙不该有 AI 目标**。默认给敌对生物装的 `MeleeAttackGoal` 会让寻路器
   去给一个 8 格宽、speed 为 0 的实体找路，而它在末地任何地方都站不下
   —— 服务端整个卡住，全部指令超时。
2. **末地的天光播种会炸**。末地是一块薄板悬在虚空里，绝大多数列的地表
   高度是 0 而邻居高达 120；`seedSky` 的判据（邻居比自己高就入队）在那里
   让几乎每一格都成为传播源，一个区块三万条。改成：没有天光的维度根本
   不播种，读隐含值 —— 那正好就是下界与末地该有的样子。代价是地下纯黑，
   所以补了一个环境光底数（下界 0.30）。
3. **网格上传要限流**。原来结果回调里当场上传，正常游玩没问题（结果零零散散
   地到），但换维度那一下几百个子区块会在几帧里全部回来 —— 软件渲染下足以
   把主线程占死几十秒，连网络回调都跑不上，表现是"指令超时"而服务端早就
   回过话了。顺带修掉一个真 bug：换维度后在飞的网格会照样上传，
   新维度里会浮着几片旧维度的地形。
4. **区块卸载要限流**。换维度时整个上一个维度的几百个区块会在同一刻全部
   到期。与 `generationQuota` 同一个道理：配额不改变总工作量，只决定它怎么摊。

## M17 多人 + 性能 + 终验（2026-08-31）

提交 `71f9ae6`。

### 多人

`tools/mp-server.mjs` 是一个**零依赖的 WebSocket 服务端**。本项目不用 npm，
而 WebSocket 的服务端侧其实很小：一次 HTTP Upgrade 握手加一个帧编解码器；
麻烦的客户端侧由浏览器提供。

它 `new` 的是**同一个 ServerCore**。"ServerCore 不含任何 Worker/DOM 依赖"
这条从 M2 立下的规矩到这里才兑现全部价值 —— 多人与单人的差别只有两样：
传输换成 socket、tick 由 setInterval 驱动。客户端那边 `?server=ws://…`
切过去，`ServerHost` 接口一个字没改。

玩家同步复用生物那条链路（订阅差集），但玩家**不进** MobManager 的生物表
—— 进了会被 AI tick、被刷怪上限计数、被 `killall` 清掉。

**三个被这条链路逼出来的真 bug**：

1. **指令从来不自己 flush**。原来靠主循环的 `sendPlayerPosition` 顺带 flush，
   而主循环有若干条提前返回的分支（开着菜单、死亡界面、还没 spawn）。
   走到那些分支时指令会一直躺在出缓冲里，表现是"指令超时"而服务端根本
   没收到。单人模式下碰巧总能走到 flush，所以一直没暴露。
2. **WebSocket 握手的魔法串写反了**：最后一组是 `C5AB0DC85B11`，那个 C
   在开头不在结尾。写反了服务端照样回 101、连接照样建立，但浏览器会在
   校验 `Sec-WebSocket-Accept` 时**静默断开** —— 服务端只看到"有人连上
   又走了"，一个字节的应用数据都没收到。
3. 原来只有"发给某一个人"的聊天，多人模式下没有任何交流手段。

### 性能

`tools/perf-check.mjs`。三个数各自说明什么，以及**必须在真显卡上量**
（CI 容器是 SwiftShader 纯 CPU 软件渲染，视距 2 就只有 4fps —— 那不是
这份代码的性能，是没有 GPU 的性能），都写在工具头部的注释里。

容器里量到的、**与 GPU 无关因而作数**的两个数：

| 指标 | 实测 | 验收线 |
|---|---|---|
| 服务端每刻 | **3.39 ms** | ≤25 ms |
| 十分钟堆漂移 | **×0.90**（30.0 → 27.0 MB） | 平坦 |
| 指令往返（多人，两标签页） | **50.5 ms** | <100 ms |
| 客户端 fps | 3.4（软件渲染，不作数） | ≥60，**待真显卡复测** |
